The continuity problem

How can several agents and projects recover durable context without copying private notes into every new session or depending on brittle keyword search?

Local-first memory layer

I designed a dual-backend memory layer that pairs portable JSON records with SQLite/FTS search, hybrid semantic and full-text retrieval, an embedding cache, incremental synchronization, and a mem command-line interface. A local dashboard and watcher make ingestion and health visible rather than leaving the system as an opaque vector store.

Retrieval with provenance

Memory Hub is designed to return context that is both relevant and traceable. Each record keeps its source, timestamps, tags, and—when it can be established without guessing—its project, contributing agent, original file path, and document section. That means a result can answer not only “what seems useful here?” but also “where did this come from?”

Retrieval combines embedding-based semantic similarity with SQLite FTS5/BM25 keyword ranking. Semantic search helps surface related ideas; keyword ranking protects exact technical details such as function names, URLs, error messages, and project-specific language. Results can also be narrowed by project, agent, source, or tag.

For information that changes over time, the CLI supports keyed upserts. A stable source + keyidentifies one logical fact, so a corrected preference, decision, or project status replaces its earlier version instead of creating a second, contradictory record. The system keeps the record’s identity, refreshes its content and embedding when needed, merges its tags and metadata, and queues the newest version for backup.

Design constraints

The design needed to balance portable project context with a query path fast and inspectable enough for ordinary work. Watermark-based incremental sync, deduplication, provenance, and local-only operation are treated as first-class constraints.
